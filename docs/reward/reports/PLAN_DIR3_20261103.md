## 1. 陈述写什么

格式（暂定，英文和现在的提示一致）：

```
<observe>where=left; face=no; dist=far; missing=frame</observe><action>turn_left|turn_left|</action>
```

| 项 | 取值 | 真值怎么算（模型这一回合看到的那一帧的位姿） |
| --- | --- | --- |
| where：目标在哪 | in_view / left / right / behind | 在画面内：物体中心投影在画面里且在相机前（`score_with_visibility` 的 objects[]：center_uv、all_corners_in_front）。不在画面内：把物体中心变到相机坐标（`canonical_task_metrics_v2._Context.to_camera`），看水平方位角，偏离正前方 135° 以内按左右分，更大算 behind。 |
| face：看清了一面没有 | yes / no | `visibility.targets[字母].visible`，即环境的 face_visible_v3 规则 |
| dist：远近 | near / mid / far | 绝对距离题按离要求距离的偏差分：太近 / 合适 / 太远，"合适"用成功判定自己的容差。其他题用相机到物体底面的水平距离（`footprint_distance`）分三档，边界取 C0 全部画面的三分位，训练前定死（决定 2）。 |
| missing：还差哪个条件 | none，或 frame / clear / relation 中的一个或几个（按这个顺序写） | 成功条件里值为 False 的那些（`gates`），用 `evaluation.progress_groups` 归成画面 / 看清 / 关系三组 |

- **两个物体的题型**（等距、同框、左右关系）：where 和 face 两个物体各写一次，例如 `where=A:left,B:in_view; face=A:no,B:yes`。
- **遮挡题：** "目标"指被挡住的那个，遮挡物不写。
- **长度：** 主线估计每回合多 20–30 个 token。C0 的 SFT 数据每个 epoch 会多约 6%。
- **已知误差：** 遮挡物按包围盒算。P1 线 10-21 到 10-23 查过，床、饮水机、多人沙发等有误判。face 和 missing 两项会带上这部分误差，但这和环境的成功判定是同一个误差，所以陈述的标签和奖励是一致的。

## 2. 真值和 SFT 数据

- **位姿：** `models_runs/sft_v10_newformat_20261024/`。
  - `sft_trajectories.jsonl`：11,095 段对话、28,654 个用户回合。
  - `frames.jsonl`：每个回合画面的 c2w，用图片文件名对上，28,654 个全有。
  - `rows.jsonl`：题目行。
- **算法：**
  - 遮挡物照环境的 `_visibility_occluders` 建：`CollisionDetector().load_scene_from_gs_root(...)`，再 `OccluderSet.from_detector(...)`，每个场景建一次。
  - 然后每帧调一次 `score_with_visibility(row, c2w, occ)`。
- **先核对一致性（CPU，不占卡）：**
  - 用 `eval_test_v2/sft_q3formal_e8/results.jsonl` 里带轨迹的结果：每回合有 failed_gates，开头有 start。
  - 注意 failed_gates 是这一回合动作之后的位姿：第 t 回合看到的画面，t = 0 是 start，t > 0 是第 t−1 回合的 failed_gates。
  - 我算的 missing 必须和 failed_gates 归组后的结果逐回合全部相同。不全同就停下查，不往下做。
  - 同时测每帧的耗时，用来估 28,654 帧的总 CPU。估计 1–3 CPU 小时，登录节点 4 核可以跑。超过 4 核能在几十分钟内跑完的量，就改用单卡 sco 任务。
- **新的 SFT 数据：**
  - 每个助手回合的 `<action>` 前面插入这一回合的陈述；
  - 系统提示加一段陈述格式的说明；
  - 写到 `reward_runs/sft_statement/`，C0 的数据只读不改。
  - 核对：对话数、回合数和 C0 相同；陈述数 = 回合数；随机抽 50 条人工看。

## 4. RL：陈述怎么给分

**推荐做法（决定 3 的甲）：** 陈述 token 有自己的优势，动作 token 照 S0。

- **动作 token：** S0 回报的组内比较，和 rw_s0 一样（S0 的奖励和筛选）。
- **陈述 token：** 只在每回合陈述那一段上加一项：
  - 这一回合陈述的准确率（对的项数 ÷ 项数，0–1）；
  - 减去整批回合的均值，除以整批回合的标准差，乘权重 0.5。
- **用现成的通道：** 方向 1 的每回合记录和 token 范围已经过了冒烟核对（范围正好盖住回答）。要加的是回答里陈述那一小段的范围。
- **为什么不加进整局回报：** 加进回报，陈述分就会流到动作 token 上。策略可能为了"好描述"去走到容易说对的位置。只给陈述 token，动作就不受它牵动。
- **和 rw_tc1 走样的关系：** rw_tc1 的问题出在逐回合项和回合长短（动作数）挂钩（见 `ROUND1_P2_20261103.md` 第 6 节的离线核对）。陈述是固定格式、长度几乎不变，这个风险小。冒烟时还是要按回合长度分开核一次。
- **乙：** 把 λ × 每局陈述平均准确率加进 S0 回报，λ = 1，成功是 5，照常 GRPO。代码最少，但有上面说的牵动动作的问题。
