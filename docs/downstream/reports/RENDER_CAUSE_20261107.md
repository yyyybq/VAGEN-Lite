# 模拟器画面坏的原因和修法（2026-11-07）

写于 2026-11-07 00:3x UTC，初稿（核查前）。起因：D3 可解检查里 28 个场景没过渲染检查（[D3 计划](D3_PLAN_20261106.md) 第 2 节），在登录节点上单进程查了约 40 分钟（不占卡）。实验脚本、日志和改好的副本都在集群 `downstream_runs/n/d3_trial_20261106/rootcause/`。

## 结论先说

- **原因找到了，已修（56270ef2）。**
  - RoboCasa 每次重置都新建一套模拟器和渲染上下文，旧的不释放，只能等 Python 的循环垃圾回收来收。我们建一个场景会留下两套旧的。
  - 垃圾回收什么时候跑，取决于进程里分配了多少对象（例如 15,000 个位姿的搜索），所以有的进程坏、有的不坏，同一个场景时好时坏。
  - 旧上下文被回收时，会在"当前"渲染上下文里删掉自己的缓冲编号。当前的正是我们在用的那个，编号又是同样的小数字，于是删掉的是我们的缓冲。robosuite 之后不再切回自己的上下文，之后每一帧都读到被删的缓冲：彩色噪点、条纹，或者一直是同一帧。
  - 证据：强制回收一次，就能让一个本来好的进程从下一帧起变坏（3 / 3 好 → 0 / 3 好，可见面积 0，GL 报错 0x506）；在没修的 D3 进程里，回收发生在位姿搜索当中，接着渲染检查就没过（3 个场景都是这样）。
- **修法：** 建场景时先强制回收一次，再给我们的上下文重建缓冲，约 1 秒（`downstream/n/n_env.py` 的 fresh_render_context）。N 系列所有建场景的脚本都经过它：出题、评测、问答、D3。
  - 验证（修好的副本，真的 D3 出题流程，位姿搜索就在同一进程里）：CoffeeSetupMug_s3000、ScrubCuttingBoard_s1001、StoreLeftoversInBowl_s1000 各 3 次，StirVegetables_s1000、SearingMeat_s1013、TurnOffStove_s1001 各 1 次，12 次都通过全部渲染检查。没修时这 6 个场景在任务里都没过。
  - 测试：集群上 N 系列 48 个测试通过（含新加的 1 个）。
- **它解释了：**
  - 11-06 坏画面复查里"从第一轮起就坏"和"中途停住"的回合（推断：机理相同，没逐个回合复现）；
  - 11-03 记下的"诊断任务里 20 张全好，只在真任务里出现，猜是资源吃紧"（那条推断可以撤了：是回收时机，不是资源）；
  - D3 里 28 个没过检查的场景中的 14 个（可见面积约 0 的那一半）。

## 已有结果受影响的地方

1. **N1 的出题记录。** 出题和评测用同一套渲染，出题时的可见面积检查如果做在坏帧上，"这个实例可解"可能不成立。
   - 按图像粗糙度粗筛（没逐张看），N1 的 600 个实例里 45 个的出题图（起点、最短、最舒服三张里至少一张）像坏图。
   - D3 里另外 14 个没过检查的场景（可见面积不为 0、但和记录不同）就是这种：14 个的出题图都像坏图；在修好的干净进程里重渲染，可见面积和记录对不上。例：OpenDrawer_s3002 干净进程两次都是 0.061，记录是 0.0052；PackIdenticalLunches_s1003 画面占比那道是 0.00285，低于 0.003 的门槛，记录里却过了。
   - 出题图坏，不等于记录一定错：可见面积是先算的，图是后存的，中间可能正好发生回收（SearingMeat_s1013 就是图坏、记录对）。所以要逐个重判才知道。
2. **评测回合。** 评测里的坏帧回合，11-06 的复查已标出，按你定的剔除规则处理。修好以后的新评测应该不会再有这种坏帧（推断；照样扫）。
