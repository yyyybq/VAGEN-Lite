## 0. 总目标与硬规则

目标：在 BEHAVIOR-1K（2026 挑战设定，100 个任务）的官方评测流程下，用"强模型高层调度 + 现成动作执行器 + 可插拔的检查/恢复/记忆等模块"，把任务进度分数（Q-score）尽可能刷高。不参加正式提交，但评测器、版本、观测限制一律按官方来，否则分数没有可比性。

三条硬规则：

1. **性能优先，trick 不限。** 任何能涨分的做法都可以加，前提是满足规则 2 和 3。
2. **模块化红线（第 4 节）。** 每个 trick 必须是一个独立模块，用一个配置开关就能整体去掉，去掉后系统照常运行。加进去就拆不开的东西，不允许合入。
3. **消融必须可做（第 6 节）。** 任何涨分都要能通过"同任务、同实例、同 seed、同预算，只改开关"的对照来归因。调参只在开发集做；报告集只跑冻结后的配置。

执行纪律：先跑通再加模块；真实 episode 跑过才算有效，mock 和单测不算；始终区分"计划实现 / 已写代码 / 接口验证过 / 模拟器实跑过 / 有完整评测成绩"五种状态，不用占位实现或编造数值冒充交付。

## 2. 工作方式

- **NFS**：大量小文件（缓存、逐步日志）优先写本地盘，再把摘要同步到 NAS。
- **代码**：新建独立 git 仓库（建议 `/nas/baiqiao/b1k_agent`，名字可改），小步频繁提交。不直接修改 BEHAVIOR-1K 和 openpi 的工作树；必须改时用独立分支或 patch 文件，并写明上游 commit。

- **进度**：维护 `STATUS.md`（当前阶段、已验证事项、阻塞、下一步），每个里程碑更新。另写 `CLAUDE.md`，固化本项目的运行命令、模块化红线和 GPU 纪律，供后续会话继承。

## 3. 前几步的顺序与完成标准

**Step 1 接管盘点。** 读 `b1k_runs` 里的脚本；记录 BEHAVIOR-1K 实际 commit、OmniGibson/Isaac Sim 版本、openpi commit；读检查点的配置（动作维度与单位、相机顺序、归一化统计、动作块长度、训练任务）；盘点 `datasets/`；记录磁盘、GPU 型号/显存/驱动。核对官方页面与仓库评测代码是否一致，写出 `docs/PROTOCOL.md` 初版。完成标准：STATUS.md 与 PROTOCOL.md 初版。

**Step 2 冒烟。** 等 watcher 的结果。通过标准：headless 渲染得到非空 RGB 和 depth、一个任务 reset 成功、连续若干步 step 不崩。失败则诊断，不绕过。

**Step 3 官方 baseline 单任务实跑。** 在 openpi 环境启动 π0.5 服务（turning_on_radio 检查点），用官方评测入口跑 turning_on_radio 的一个实例，完整 episode。保存官方 metrics、视频和自己的日志。逐项核对图像/深度处理、相机顺序、本体状态、动作维度/单位/归一化、动作块、reset、超时、终止。终止、分数和官方动作执行流程复用官方实现，不另写一套近似的评测器。完成标准：一条真实 episode 的官方 metrics 文件。

**Step 4 吞吐测量。** 单 episode 墙钟时间、单卡能并行几个模拟器+策略实例、显存占用。据此估算开发集、报告集和全量评测各需多久，写进 PROTOCOL.md。后面所有实验规模都由这个数字决定。

**Step 5 选定多任务执行器。** turning_on_radio 检查点只覆盖一个任务。按官方 baselines 页面找 BEHAVIOR 适配的多任务 π0.5 检查点（OpenPI 路线）或 GR00T N1.7 路线。对每个候选记录仓库、revision、训练任务覆盖、机器人、输入、动作维度与单位、归一化统计、动作块长度、语言条件形式、许可证；估算大小后下载。选择标准是"能下载、能加载、能按官方接口实跑"，不是论文数字最高。必须区分：π0.5 通用预训练权重 / 旧版 50 任务适配权重 / 按任务或技能训练的权重 / 新版 100 任务权重；不能因为都叫 π0.5 就互换。第一阶段只定一个主执行器，保留统一替换接口。

同时做技能指令诊断：执行器对"抓杯子""打开柜门"这类子任务指令是否真的响应。只在完整任务指令上训练的策略，不能因为上层换了一句文本就当作技能执行器。诊断结论决定 M-skill 这条线是否存在，以及是否需要最小技能微调（记为额外训练贡献）。

**Step 6 开发集 baseline。** 按任务结构选 5 个开发任务（覆盖纯导航、单物体操作、多物体、铰接物体、长程），用非报告实例，执行器单独跑。产出第 6.7 节定义的失败分布。

**Step 7 最小闭环。** 接入 M-plan、M-check（强模型）和最小的 M-recover，同条件再跑，得到第一张对照表。

之后由失败分布决定下一个模块；每加一个模块跑一次阶梯对照。不要一次性把第 5 节的模块全堆上去。

## 4. 架构与模块化红线

建议目录：

```
b1k_agent/
  configs/            # yaml；每个模块一个块：enabled / impl / params
  configs/prompts/<module>/<version>.txt
  agent/loop.py       # episode 主循环，只依赖 interfaces
  agent/interfaces.py # 接口契约
  agent/state.py      # EpisodeState：系统估计，不含模拟器真值
  modules/<name>/     # 每模块一个包：impl、null 实现、tests、README
  executor/           # 策略服务客户端与适配（π0.5 / GR00T 可换）
  providers/          # 强模型 API 封装（Astra 等，可配置）
  eval/               # 官方评测适配、批量运行、汇总、消融矩阵生成
  data/               # 技能片段、标签、经验库、蒸馏数据
  diagnostics/        # 唯一允许读模拟器真值的包；只用于离线分析与标注
  scripts/  docs/  STATUS.md  CLAUDE.md
```

接口契约（可微调，但定下来后写进 `interfaces.py` 并保持稳定）：

- `Executor.act(obs, instruction, horizon) -> ActionChunk`
- `Planner.next_subtask(obs, state) -> Subtask | None`
- `Checker.judge(obs, state) -> Judgment{status: done | in_progress | failed | unknown, confidence, evidence}`
- `Recovery.propose(obs, state, failure_type) -> RecoveryPlan | None`
- `Memory.retrieve(obs, state, k) -> list[Experience]`；`Memory.propose_adjustment(obs, state, next_subtask) -> AdjustPlan | None`
- `Scorer.score(obs, state, candidates) -> list[float]`
- `GoalManager.order(goal_spec, state) -> ordered_subgoals`；`GoalManager.regression_risk(plan, state) -> float`

`EpisodeState` 每个 episode 独立：任务、子任务计划、当前子任务、历史摘要、重试次数、持有物体估计、已完成子目标的估计。并行运行时不同实例不得共享记忆。系统估计与模拟器真值分开保存，未知就标 unknown。

红线（每条都要有对应测试）：

1. 每个模块有 null 实现，默认关闭；主循环只开 M-exec 就能跑完一个 episode。
2. 模块之间不互相 import；只通过 `EpisodeState` 的文档化字段和接口返回值交换信息。某模块需要另一模块的输出时，先在 `EpisodeState` 加字段并写文档。
3. 模块不改主循环的控制流；主循环的分支只看接口返回值。
4. 运行时代码（agent、modules、executor、providers、eval）禁止 import `diagnostics/` 和任何模拟器真值 API；用 import 守卫测试强制。
5. 提示词按模块、按版本存放；模块之间不共享提示词文本。
6. 每次运行记录完整配置及其 hash、代码 commit、检查点、提示词版本、实例清单、seed；结果表由日志自动生成，不手填。
7. 开关矩阵测试：对每个模块 on/off，用录制观测跑一个 mock episode，保证构造和运行不报错。
8. 真值隔离测试：从评测日志里删除或替换真值字段，策略的决策序列不变。
9. 新模块合入前必须附：模块 README（目的、来源论文、输入输出、触发条件、已知失败）、null 实现、单测、一次真实 episode 的开/关对照结果。

## 5. 模块清单

按预期性价比和依赖排序。"启用条件"指失败分布中该类失败明显时才加。每个模块的消融方式都是：关开关，其余不变。

- **M-exec 执行器适配。** 固定接口，π0.5 / GR00T 可换。推理参数（动作块长度、重规划频率、temporal ensembling）作为可调参数，只在开发集调，报告中同时给默认值和调后值。
- **M-plan 高层规划（强模型）。** 输入：合法观测、BDDL 任务定义、技能描述（支持的输入、能做什么、何时结束、已知容易失败的状态）、历史摘要。输出：下一子任务与技能指令。只在阶段边界、停滞或关键事件时调用，频率在开发集调。provider 可配置，优先尝试 Astra——这是我希望用的模型名称，不是已核实的 API model ID；先检查项目配置和实际可用接口（视觉输入、结构化输出、限流、费用），不要猜模型标识；缺访问能力时做成可配置 provider 并继续不依赖真实调用的工程；替代模型实跑要明确标注，不能算作 Astra 结果。没有实现的技能不得在提示词里假装存在。
- **M-check 进展检查。** impl 可选：强模型 / 规则（本体状态加简单视觉线索）/ 小模型（后期由 M-distill 提供）。可以和 M-plan 共用一次调用，但必须作为两个接口返回，便于分别替换。输出要带可见证据。
- **M-goal 目标管理（直接面向 Q-score，便宜）。** 解析 BDDL 目标为子目标；排序（先易后难、先独立后依赖）；保护已完成的谓词（不再靠近相关物体，检测退化后优先恢复）；时间临近耗尽时切到低风险模式而不是乱动。子目标完成状态来自 M-check 的估计，不是真值。
- **M-recover 有限恢复。** 恢复原语分两类：脚本型（只用本体状态：缩回手臂到安全姿态、原地旋转重新观察、后退）和指令型（给执行器的文本指令，前提是 Step 5 诊断证明执行器响应）。触发来自 M-check；有限重试、有限重规划；网络超时或输出无效时走确定、可记录的回退。恢复受同样的观测限制、时间预算和动作限制。
- **M-approach 站位与接近调整。** 用深度估计到目标距离，把底盘调整到可操作距离。启用条件："到达但够不着 / 站位不对"占比高。
- **M-memory 经验库与检索。** 先做"检索参考"：从示范和开发期成功轨迹建库，按技能、对象语义、视觉状态检索少量经验作为 M-plan / M-check 的证据，记录每条来源；这一步可以称为 RAG。确认技能交接失败明显后，再做"状态调整桥接"：检索下一策略可接手的候选状态，局部打分，用允许的感知和控制生成调整动作，执行后复核。跨场景不重放绝对关节轨迹。报告评测时经验库和参数全部冻结，只在单个 episode 内更新任务记忆。
- **M-skill 技能片段数据与技能执行器。** 前提：Step 5 诊断显示执行器响应技能指令，或决定做最小技能微调。数据接口见第 7 节。
- **M-score 动作/阶段评分。** 从混合质量数据学习动作与阶段成功评分；推理时多候选选优。相同候选数和推理预算下与原策略比。不把预测分数称作官方 Q-score。后期。
- **M-distill 小模型检查/切换器。** 用强模型在合法观测下的判断作标签训练小 VLM，替换 M-check 的强模型 impl 以降低 API 成本。标签可用真值辅助核验，小模型输入只含合法字段。先迁移"是否完成、是否切换"这类边界清楚的能力。
- **M-spatial 空间记忆。** 只在失败明确指向空间记忆或几何精度时考虑；先验地图、实例标签不是合法输入。
- **M-explore 在线探索。** 探索预算、测试时 agent 参与、跨实例信息都要单独核实；默认关闭。

系统级要求：强模型等待时模拟器是否暂停、动作是否继续，按官方控制循环实现，不能靠改变时间推进方式获得优势；执行前检查高层决策对应的观测是否已过时。

## 6. 实验协议

**6.1 任务与划分。** Dev 任务先 5 个，稳定后扩到约 20 个；Full 为 100 个，只在配置冻结后跑且次数有限。实例：官方报告实例（截至 2026-10-21 的信息是 0–9，执行时核实）作为 Report；其余公开实例作为 Dev。不用 Report 实例调提示词、选记忆或挑重跑。可选 S2 留出任务：从一开始把约 10 个任务排除在所有采集、标注、训练、调参之外，供后续论文的泛化主张使用。

**6.2 确定性与 seed。** 先测固定 seed 下 episode 是否可重复。不可重复则每个 (task, instance) 跑至少 3 个 seed，报告时给区间（按任务分层 bootstrap）。

**6.3 预算。** 官方步数与超时上限不变。强模型调用次数、token、费用、墙钟时间全部记录。对照组之间预算一致，并包含一个"无指挥但同等重试次数、固定重试规则"的预算匹配对照，防止增益来自多给了时间。

**6.4 指标。** 主指标：官方 Q-score，按官方汇总方式（任务内平均后跨任务平均）。次指标：完整成功率、子目标成功率、谓词退化次数、恢复尝试/成功数、无效重复动作数、调用次数与费用、耗时。基础设施错误单独计数。子集均值与全量分数分开展示，不把不同任务集合的高分拼成一张总榜。

**6.5 补跑规则。** 模拟器崩溃、服务超时等基础设施错误：同 (task, instance, seed) 最多重跑 2 次并记录。策略失败一律不重跑，不挑最好结果。

**6.6 消融矩阵。** 前向阶梯：L0 执行器单独 → L1 +M-plan → L2 +M-check → L3 +M-goal → L4 +M-recover → 之后每级只加一个模块。最终配置做 leave-one-out。两套都在 Dev 上做；最终配置和阶梯在 Report 上各跑一次。某组必须更换权重、输入、数据或预算时，在表旁标注。不能只比"原始执行器"和"最终系统"就把增益归给某个模块。

**6.7 失败分类。** 每条失败记录视频时间位置、当前技能、模型当时的判断、实际执行结果、后续动作。类别：环境/服务错误 | 目标识别 | 任务顺序 | 到达与站位 | 抓放操作 | 技能切换与交接 | 恢复无效 | 谓词退化 | 原因不确定。只凭最后一帧不下结论。

## 7. 训练数据与迭代轮次

**7.1 数据接口先建好。** 技能片段至少保留：源轨迹与数据版本、任务/技能指令、原始起止索引、同步观测与动作、完成标签及其来源（官方标注 / 真值规则 / 强模型 / 人工）、整条 episode 结果、训练/开发划分、round 字段。片段按源轨迹隔离划分，避免相邻片段分到两边。优先用官方子任务边界；缺失或错误才用强模型辅助标注，并抽查边界、对象和完成状态。一条最终失败的轨迹里成功的局部片段要保留。

**7.2 三类数据通路。** policy observation（正式运行可见：RGB、depth、本体状态、BDDL 任务定义）/ training annotation（训练与标注可用真值）/ evaluation record（评测后分析用的官方结果）。每个字段标注属于哪类。评测时不把物体位姿、全局机器人位姿、真实分割、内部物体状态、全场景地图、谓词真假、实时得分交给任何模块或它们调用的工具；现成导航、抓取、IK、规划工具若内部读真值，先替换数据路径。

**7.3 蒸馏数据。** 每次强模型调用保存：输入（合法观测摘要与状态）、输出（子任务选择、继续/切换、失败判断、恢复选择）、简短可见证据、事后用真值核验的正确与否。不依赖不可获得的内部思维链。

**7.4 轮次。** 永远冻结：Report 划分、评测器版本、每 episode 预算。第 0 轮不训练（Step 6、7 产出失败分布与决策日志）。第 k 轮：固定预算采集 → 标注 → 只训练一个可训练部件（技能执行器 / 评分器 / 小模型检查器 / 经验库，四选一）→ 冻结 → Dev 评估 → 决定保留或回退。每轮产物按 round 和来源记录，可随时回退到任一轮配置。跨 episode 在线学习默认关闭；若研究它，先定规则和固定顺序，单列结果。

**7.5 示范数据。** 先盘点 `datasets/` 现有内容；需要更多示范时按任务子集下载，先估算大小。
