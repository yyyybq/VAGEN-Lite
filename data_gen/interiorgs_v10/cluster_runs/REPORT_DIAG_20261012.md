### b. 配额截断前的可行候选

中间产物**没有**保留"完整可行候选数"。原因：分配是惰性的，按 item 轮转，每认证到一条落在未满档的候选就停一次，
14 条配额满了就整体停止，后面的 item 和候选从未被检查；每个 item 还有认证上限（48 次认证 / 1,500 个检查）。
保留下来的是已经认证、通过全部过滤（合法、未成功、≥1 目标可辨识、终帧可辨识、多样性）的候选数 =
`init_candidates.accepted + band_quota_full`（后者是落在已满档、存为 surplus 的候选）。这是**下界**。

| 940 个有 ≥1 个带终点 item 的场景 | 最小 | P10 | 中位数 | 均值 | P90 | 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| 已认证可行候选（下界） | 0 | 105 | 226 | 254 | 441 | 948 |
| 带终点的 item 数 | 1 | 8 | 22 | — | — | 58 |

* 下界 ≥ 20 的场景占 98.8%（≥ 14：99.3%）。0 的两个场景是下文的 `0062`、`0141`。
* 也就是说，配额截断丢掉了约 94% 已经认证好的候选；备选池的大部分可以直接从 surplus 取，不需要额外认证。
* surplus 按档、按族的分布没有保留（funnel 按场景合并）。
* 重新获取完整数的成本：按第 3 节配置 2 的逐 item 计时（每次认证 0.131 s、每个 item 反向搜索 0.92 s），把每个带终点 item 的
  48 次认证预算全部用完，约 **3.4 核时 / 100 场景，即约 34 核时 / 1000 场景**，与整个生成跑一遍相当（单个 I80.1 作业约 2.5 h）。
  不必做：备选池用很小的代价就回答了"每场景能否到 ≥ 20 条"（第 3 节：90% 的有任务场景可以）。

### c. occlusion_alignment 为什么是 0 条

| 指标 | 数量 |
| --- | --- |
| 生成的 item | 6,695 |
| 有终点的 item | 524（7.8%），分布在 314 个场景 |
| 采样器：必要条件为空 / 无成功位姿 / 网格无合法点 | 3,199 / 2,874 / 73 |
| 参数在 pitch 0 下不可行（被剔除的元组） | 7,622 |
| 最终任务 | 0 |

* 填充顺序：族按 projective → absolute_positioning → screen_occupancy → equidistance → occlusion_alignment 交错，
  occlusion_alignment 排第 5（最后），但它在第一轮就会被访问到（每轮每族一个 item），所以 0 条**不是**顺序造成的。
* 真正原因：`initial_states.ItemSearch` 要求终帧**所有**目标都可辨识，而 occlusion_alignment 的成功条件就是目标被遮住
  （族模块自己声明 `TERMINAL_IDENTIFIABLE_ROLES = (1,)`，只要求遮挡物可见）。两者矛盾，每个候选都在
  `terminal_not_identifiable` 被拒，每个 item 白白耗掉最多 48 次认证。
* 证据：有 occlusion_alignment 终点 item 的 314 个场景，初始态阶段 `terminal_not_identifiable` 平均 93.1 次 / 场景
  （合计 29,231），其余 626 个场景平均 12.7 次（合计 7,965）。第 3 节的 occlusion_alignment 单族对照运行直接验证。

## 4. 建议

**俯仰：暂不锁定。** 真实数据上 −15° 让可行 Projective / FOV item 多 23%（合成估计 +26%），全族带终点 item 多 17%，
但每场景 14 条的配额才是瓶颈：任务只多 1.7%、场景只多 1 个。锁定要改 env 的运动模型和动作协议、R1 检查点与评测不可比需重训、
渲染与判据要在俯仰下重新核对，并且全量重生成。等 GPU 审核数据出来后再看：如果大量任务因"低矮目标被裁掉"被拒，
或者每场景目标提到 20 条以上，再重新评估。

**族配额：开，用上面的配额，但先把上限改成软上限。** 它把 projective 从 52% 降到 41%，absolute / screen / equidistance 相应上升，
d* 分布基本不变。硬上限让"可行 item 集中在 1–2 个族"的场景少拿任务（−3%）；软上限（其他族都填不动时允许超过上限）
可以消掉这部分损失，改动很小。occlusion_alignment 的配额取决于终帧规则（见待决事项 2）：不改规则就设为 0:0 并且不再为它建 item，
否则每个场景白白耗费认证（100 个场景约 676 s，约占生成时间的 8–10%）。

**K：生成时取 16，审核时按需取用。** K = 16 的 CPU 代价约 +22%（每场景 81 → 99 s），70% 的备选直接取自已认证的 surplus；
90% 的有任务场景主集 + 备选 ≥ 20 条。备选只在审核刷掉任务的场景里渲染和审核，GPU 成本只随实际拒绝数增长。
如果必须预先审核全部备选，K 应按预计拒绝率取：v1 的 RGB 审核通过率 47%（211 → 100，但当时要求每帧两目标都可辨识，
比 v10 严），按 30–50% 的拒绝率，K = 6–8 足够把每场景补回 14 条。
