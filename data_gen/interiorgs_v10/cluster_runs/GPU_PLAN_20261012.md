# GPU 阶段计划（只写计划，本轮没有提交任何 GPU 作业）

2026-10-12

## 结论

- **审核模型：** 推荐用集群上已有的 Qwen3-VL-8B-Instruct 做主审、InternVL3.5-8B-Instruct 做第二审。两个模型对每一项的回答按现有合并规则合并：多数票，打平按"不通过"算。
- **先试点，再全量。** 全量之前先做一次 200 道题的试点，同时有人工按同一份问卷标注。用它来量出模型和人的一致程度，以及真实的 GPU 吞吐。
  - 原因：v1 的审核不是集群上的模型做的。v1 审核记录里审核人一栏是 `assistant_direct_visual_inspection`，也就是对话助手直接看图审的。所以目前没有任何一个模型在这类图上验证过。
- **GPU 时间估计：** 正式题渲染约 2 GPU·小时。两个模型各审一遍约 2–6 GPU·小时。后备题按需再加约三到五成。总计约 5–10 GPU·小时，用一个 8 卡节点大约 1–2 小时就能跑完。
  - 这个估计里，渲染速度是实测的，审核速度是推算的（推算依据见第 5 节），以试点实测为准。
- **需要你确认或提供的事**见第 6 节：模型选择、200 道题的人工标注、GPU 节点和配额。

## 2. 每道题审什么

审核图是渲染出来的画面，上面用彩色框标出目标：A 红色，B 蓝色。框只画在审核用的副本上，训练用的图不画框。

### 每道题都要审的项

**题目本身（每道题审一次）：**
- 框里的物体是不是写的那个类别。
- 描述能否唯一指向它，即画面里没有另一个同样符合描述的物体。
- 这道题能不能做到。

**每一帧：**
- 渲染是否正常，没有大片黑块或破碎。
- 每个目标能不能认出来。
- 框是否落在物体上。

**判定规则（已写在 `configs/admission_v2.json`，代码在 `admission.py`）：**
- **拒绝，这道题作废。** 适用于以下任一情况，并且同一物体或同一对物体以后不再出题：
  - 类别不对；
  - 描述不唯一；
  - 做不到；
  - 终点画面里框没落在物体上，或者有两帧以上框没落在物体上。
- **起点画面：** 至少一个目标能认出来，否则暂缓。暂缓的意思是这题本身没错，这一轮先不收，以后可以重渲染或重审。
- **终点画面：** 所有目标都能认出来，否则暂缓。occlusion_alignment 例外，见下表。

### 每个族的终点要求

| 族 | 题意 | 终点画面要认出的目标 | 额外的问题 |
| --- | --- | --- | --- |
| projective_relations | 从你的视角看，A 在 B 的左/右/前/后 | A 和 B | 无 |
| absolute_positioning | 离 X 大约 d 米，并且 X 在画面里 | X | 无 |
| screen_occupancy | X 占画面竖直方向大约 k，并且从上到下完整可见 | X | 无（X 上下被画面切掉时，"能否认出"和"框是否对齐"会反映出来） |
| equidistance | 离 X 和 Y 一样远，并且两者都在画面里 | X 和 Y | 无 |
| occlusion_alignment | 让 X 躲到 Y 后面，看不见 | **只要求 Y** | **"红框位置上的 X 是否被 Y 挡住了？"** |

**occlusion_alignment 的终点画面单独处理：**
- 审核图上照样用红框画出 X 的投影框（也就是 X 被挡住的位置）。
- 问卷里多一个字段 `target_hidden_by_occluder`，审核提示里也加了一段专门说明。说明的意思是：这一帧里 X 本来就应该看不见；请如实回答 X 能不能认出（预期是不能），不要因为红框里的东西被挡住就说框没对齐。
- 回答"没被挡住"就拒绝，理由是 `terminal_target_not_hidden`，这对物体以后不再出题。例如遮挡物的框比实际挡住的范围大，像镂空的家具。
- 回答"不确定"就暂缓。
- 这一帧里 X 的框是否对齐不计入作废判断，因为 X 被挡住了，本来就看不见框是否对齐。

相应代码和测试在 `admission.py`（`HIDDEN_TARGET_FAMILIES`）和 `tests/test_admission.py::test_occlusion_alignment_terminal_rule`。

## 3. 后备题按需使用的流程

每个场景除了 14 道正式题，还最多准备了 16 道后备题（`tasks_reserve.jsonl`）。后备题只在需要时才渲染和审核。

1. **第 1 轮：** 只渲染、审核正式题，每道题平均要审约 3.3 帧，包括起点、终点和 SFT 每轮的分段点。
2. **收题：** 用 `admission.admit` 收题。用 `release.scene_stats` 和 `release.plan_regeneration` 算出每个场景还差几道，以及哪些物体或物体对已被拉黑。
3. **从后备里拿：** 用 `release.take_from_reserve` 为差题的场景取后备题。
   - 按存好的顺序取，跳过已审过的题、用到拉黑物体的题、以及物体组合等于拉黑物体对的题。
   - 还没达到最少数的族优先，已到上限的族排最后。这和出题时的软上限一致。
   - 取多少由 `plan_regeneration` 决定：差几道，再按这个场景的通过率放大，例如差 2 道、通过率 50% 就取 4 道。
4. **第 2 轮：** 渲染、审核这些后备题，再收一次。还差就重复，最多 3 轮，或者直到后备用完。
5. **仍不够的场景：** 后备用完还是不够 14 道的场景就保持不足，不再在 GPU 阶段重新出题。是否要回到 CPU 阶段为这些场景重新出题，看试点结果再定。

**代码状态：**
- `take_from_reserve` 本轮已写好并有测试（`tests/test_admission.py::test_take_from_reserve`）。
- 驱动脚本（读审核结果、调用上面三个函数、写出下一轮要渲染的清单）还没写。它很薄，大约 100 行，试点前补上。

## 4. FOV（两物体同框）族的标定

本轮没有加入 FOV 族，原因见 `STATUS.md` 第 2 节。

**如果以后要加：**
1. 用 R1 的 FOV 出题规则，在一部分场景上出一批 FOV 候选题，约 300 道。
2. 渲染终点画面。这一步只需要几分钟 GPU。
3. **人工盲标：** 标注人不知道哪些题是机器判"合格"的，只回答"两个物体是否都清楚地在画面里"。至少要有 100 道人工判为合格、100 道人工判为不合格。R1 现有的标定只用了 15 道人工通过的题，没有不合格的反例，所以无法知道门槛放进了多少坏题。
4. 用这批标注重新确定 FOV 的画面门槛，让放进来的坏题比例低于一个可接受值（例如 5%）。之后才把 FOV 加入配额。

**GPU 成本**可以忽略。**真正的成本是人工标注**：约 300 道题，每道看一张图，大约 1–2 小时。

## 5. GPU 时间估计

下面的"正式题"按本轮全量运行的正式题数算（见 `REPORT_FULLRUN_20261012.md`）。

**渲染（实测速度）：**
- 来源：`dense_score_renderer_microbenchmark_20261008`。1 张卡在 256×256 分辨率下每秒渲染约 33 帧。12 个场景的预热（加载场景）用了 57–70 秒，也就是每个场景加载约 5–6 秒。
- 正式题每道平均 3.3 帧，在上一轮 100 个样本场景的出题结果上实测。本轮全量有 13,200 道正式题，约 4.4 万帧，渲染约 22 分钟。
- 945 个有题场景每个加载一次，约 1.5 小时。
- 合计约 2 GPU·小时。

**审核（推算，试点时实测）：**
- 每次审核请求是一道题的约 3.3 张 256×256 图，加上约 1,000 字的问卷，输出约 300–500 个 token 的 JSON。
- 8B 模型在 vLLM 上批量推理，估计每张卡每秒 1–4 道题，所以 13,200 道题每个模型约 1–4 GPU·小时。两个模型共 2–8 GPU·小时。
- 这个范围较宽，因为图像 token 的数量和输出长度都会影响速度。试点 200 道题就能把它缩到 ±30% 以内。

**后备题：**
- 只在差题的场景用。如果正式题通过率在 60–80%，大约要再审正式题数量的 30–50%，渲染和审核时间也按这个比例增加。

**试点本身：**
- 200 道题，渲染加两个模型审核，不到 0.5 GPU·小时。
- 人工标注同样 200 道题，约 2–3 小时人工。

**合计：** 约 5–10 GPU·小时。
